# Trust and operational boundaries

[简体中文](SECURITY.md) | **English**

teeproxy, the Agent, their host and approved policies are within the trust boundary. Loopback HTTP is the default; a specific local IP, `0.0.0.0` or `::` is configurable. Every listener requires a nonempty API key. Prompts, responses and that key do not use TLS on the Agent→teeproxy leg, so network access requires a trusted network or protected channel. Older desktop settings without an IP continue using `127.0.0.1`.

teeproxy neither creates a local CA nor intercepts provider TLS. It connects only to the fixed Router HTTPS origin in its configuration. Every new upstream connection must pass hardware attestation, reviewed software/boot policy and current TLS-channel binding before business credentials/data are sent. Missing certificate materials, unknown policies, expired, debug or unsigned evidence are rejected without an unverified fallback.

Defaults are `127.0.0.1:8899`, 128 client connections, 16 in-flight requests and 512 MiB per model body, including after gzip decompression. Evidence/capability queries have separate limits. Request-read timeout is 30 seconds; first Router response-header timeout is 300 seconds (configurable); Router's own read-only queries use 90 seconds; stream-idle timeout defaults to 120 seconds. Slots remain held through stream completion/failure/cancellation. Connections are reused only after the response is fully read; cancellation/errors close them. Sent requests are not replayed. Upload-read failures return 400; only size violations return 413.

The Agent listener accepts only `GET/HEAD /v1/models` and `POST /v1/responses`, `/v1/messages`, `/v1/chat/completions`. Catalogs use a platform cache; only the three generation endpoints forward to Router. Unknown paths return 404 and wrong methods return 405 without an upstream connection. Health queries are internal protocol negotiation after TEE verification. teeproxy does not parse provider bodies; the verified Router enforces Agent/provider compatibility, account/price constraints, usage and refusals. Saved routing rules accompany every business request and are enforced before upstream calls. Response routing metadata is display-only; absent, malformed or different metadata does not cause teeproxy to discard a response.

Platform catalog 401/403 responses revoke the cache, stop listening and end active client streams. Page refresh and local `/v1/models` share this behavior even while minimized; a delayed failure from an old identity cannot affect a new identity. Network errors, timeouts, 429, 5xx and malformed responses do not trigger shutdown, nor do model-endpoint business refusals.

Host must match the actual local destination IP and port; `localhost` is allowed only for loopback destinations. URIs must use origin-form allowed API paths. CONNECT, absolute target URLs, browser requests and administrative APIs are rejected. Any Origin, including `null`, is rejected. Native Electron clients such as VS Code Copilot may send no Origin with `Sec-Fetch-Site: none`, `Sec-Fetch-Dest: empty` and API fetch modes `no-cors`, `cors` or `same-origin`. All three fields must appear exactly once. Web-origin, navigation and ambiguous headers remain rejected; no browser CORS is enabled. These local Fetch Metadata headers are not forwarded. API-key and Host checks still apply. An incoming Host never selects or changes the upstream destination.

`client_key_env` is required. Keys must contain 16–256 visible ASCII characters; an empty configuration cannot start the proxy. All Agent endpoints, including the catalog, require the exact configured key. Missing, empty or wrong keys return 401 without querying the platform or connecting to Router. Wildcard listening does not relax Host validation. teeproxy strips Agent authentication, cookies and hop-by-hop headers, then sets Router authentication. Additional custom headers may still be forwarded, so do not put unrelated service keys in them. Bodies, answers and authentication values are not logged. Responses force `Cache-Control: no-store`.

Windows keys are DPAPI-encrypted in current-user scope and used in local memory at runtime. The Agent key loads and displays in full for local authentication, without upload to the platform. Signing keys live in `data/identities/`; the platform holds only public keys. Sessions and admission credentials live in `data/identity.dpapi`. Current versions do not use usernames/passwords. Logout or expired authentication stops the old identity's proxy and clears session/private lists, preserving local identity and proxy settings. Financial records are not persisted locally. Logs exclude business content and keys. Stop waits for listeners/connections to close before restart. Minimize/close hides to tray and continues forwarding; **Exit teeproxy** terminates the process. If the tray is unavailable, closing exits.

Router and its cloud platform must supply a boot chain matching approved policies. Attestation does not establish which model the provider actually executed or imply zero upstream logging. Bundled approval policies are empty. Test and historical signed samples are neither approval of a live deployment nor a production security audit.

Login issues a separate, narrowly scoped Router admission credential. The desktop encrypts it with session state and renews it through the platform session, including while minimized. Before attestation, only this token is sent as `X-Router-Access`; business credentials remain confined to the same verified TLS connection. Health negotiation also uses it. CLI users supply it through `router_access_env`. It never becomes an Agent API key or an upstream header.

Agent `/v1/models` exposes only standard `id`, `object`, `created` and `owned_by`, deduplicated by ID. Merchant, pool, account, multiplier, quote and cache data remain in the UI. Generation responses remove `X-Router-*`, `X-Teeproxy-*`, cookies and server implementation information, preserving original bodies, SSE, usage, errors, request IDs and rate-limit/retry headers.

Model requests additionally require Ed25519 signatures generated by teeproxy over the body, routing rules, headers, timestamp, nonce and current Router boot ID. Private keys exist only in portable `identities/*.dpapi`; the platform receives public keys and signatures. Router identity derives from the public-key digest; a platform Bearer alone cannot impersonate it. Logout preserves signing credentials. Moving devices requires recovering that identity, not silently replacing it by logging in again. Sessions/caches remain identity-scoped; separate mappings preserve financial accounts and historical merchant limits.

Registration/login use no username/password. A locally generated Ed25519 public key determines identity. The platform stores the public key and verifies possession using single-use, purpose- and origin-bound challenges. Router finds the public key in configuration; model requests carry only the ID and signature metadata.
